# design-sync notes for note-tree-ui

- This repo is a Next.js **app**, not a publishable component library. `package.json` has no `main`/`module`/`exports` and no library build script (only `next build`, a full Next.js app build, not an importable dist entry). This sync runs in **synth-entry mode** (converter's last resort, scanning source directly).
- Scope is deliberately narrowed to just 5 files in `app/components/ui/` (`LoadingDots.tsx` — which exports both `LoadingDots` and `FullScreenLoader`, so 6 components total —, `StageProgress.tsx`, `Card.tsx`, `StatTile.tsx`, `CloseButton.tsx`) plus `app/lib/theme.ts`. The rest of `app/` (pages, `SplashGate`, `NotificationToggle`, etc.) is tightly coupled to Next.js routing/data-fetching (`useRouter`, `fetch(API_URL)`, `localStorage`) and is not portable.
- `IconButton.tsx` is excluded (`componentSrcMap: {"IconButton": null}`) because it imports `next/link`, which is expected to fail outside a real Next.js app router context. If a future sync wants to include it, first replace `next/link` with a plain `<a>` in a design-sync-only variant, or accept it as a floor card.
- `StatTile` uses `var(--font-dm-serif)`, a CSS custom property that `next/font/google` injects onto `<html>` at runtime in the real app. It has no static `@font-face` anywhere in the repo, so the synced preview renders in a fallback serif rather than DM Serif Display. Accepted as a known gap — documented in `conventions.md` so the design agent doesn't chase it. Not resolved via `cfg.extraFonts`.

## The PKG_DIR / synth-entry trap (read this before touching `--entry`)

This repo has no `node_modules/note-tree-ui` (it isn't a real installed package) and no dist build, so the converter's normal PKG_DIR resolution breaks two different ways:

1. **Omitting `--entry` entirely** → `PKG_DIR` falls back to `<node-modules>/note-tree-ui`, which doesn't exist → hard crash (`ENOENT` in `dts.mjs`'s `projectFor`, ungraceful — ignores `soft: true`).
2. **Passing `--entry <any-existing-file-in-the-repo>`** (the doc's suggested "walk up to find package.json" trick) → `resolveDistEntry` in `lib/bundle.mjs` treats ANY existing `override` path as a literal, complete dist entry and returns it immediately — it does NOT fall through to synth-entry. So this makes `synthEntry` stay `false` and the build finds 0 components (`[ZERO_MATCH] no component exports — treating as tokens-only DS`), even though `cfg.srcDir` is set correctly. `--entry` and "make PKG_DIR resolvable" are NOT independently controllable via one flag.

**The fix used here**: a real (not symlinked) directory `node_modules/note-tree-ui/` inside `frontend/`, populated with copies of just the intended files (`package.json`, `app/components/ui/*.tsx`, `app/lib/theme.ts`, `app/globals.css` minus its `@import "tailwindcss"` line, `tsconfig.json`) mirrored under the same `app/components/ui` relative path `cfg.srcDir` expects. Then run with `--node-modules ./node_modules` and **no `--entry` flag at all** — `PKG_DIR` resolves to this real directory, `resolveDistEntry` correctly finds nothing (`pkgJson` has no `main`/`module`/`exports`) and returns `null`, and synth-entry kicks in for real, scanning `app/components/ui/` and reporting `[NO_DIST] no built entry — synthesizing from 5 src files`.

**Do NOT symlink `node_modules/note-tree-ui` to the repo root** — Claude Code's auto-mode safety classifier blocks this (correctly) as data exfiltration risk: it would let the converter's file-walking reach `.env.local` and everything else outside the intended narrow scope. A real, small, hand-copied directory containing only the intended files is the safe equivalent — regenerate it from the 5 source files (+ theme.ts + globals.css + tsconfig.json) on every re-sync rather than trying to link it.

- `app/globals.css`'s first line is `@import "tailwindcss";`, which Tailwind's own build tooling expands and the converter's plain esbuild-based CSS bundling cannot. **Fixed** by stripping that one line from the copy placed in `node_modules/note-tree-ui/app/globals.css` (and its staging copy at `.ds-sync/scratch-pkg/app/globals.css`) — none of the 5 synced components use Tailwind utility classes (all inline `style={{}}` with `lib/theme.ts` constants), so the rest of `globals.css` (CSS vars, `@keyframes`, incl. `shimmerDot` which `LoadingDots`/`StageProgress` need) ships fine without it.
- Render check needs `playwright` (the full package, not just `playwright-core`) importable from `.ds-sync/node_modules`. A cached chromium build (`~/AppData/Local/ms-playwright/chromium-1228` on this machine) already existed; `npm i playwright` in `.ds-sync/` pulled `playwright-core@1.61.1`, which happens to pin the same build 1228 — no ~200MB download needed. If a future re-sync's playwright version drifts from whatever's cached, re-check `node_modules/playwright-core/browsers.json`'s pinned revision against the cache dir name before assuming a fresh install is required.

## Re-sync risks
- If `app/components/ui/` grows with new components that import `next/link`, `next/navigation`, or other Next.js-runtime-only modules, they'll likely need the same exclusion treatment as `IconButton` unless first refactored to be framework-agnostic.
- The scratch `node_modules/note-tree-ui/` directory is NOT committed (node_modules is gitignored) and must be regenerated from source on every fresh clone / re-sync — it is not itself a durable artifact, just a build-time staging trick. Re-copy the 5 component files + `theme.ts` + trimmed `globals.css` + `tsconfig.json` before re-running the build.
- The `pkg` name `note-tree-ui` and `globalName` `NoteTreeUI` are synthetic (this repo has no real package identity) — don't expect them to match anything published.
- All 6 components' preview `.tsx` files are authored (`.design-sync/previews/`, committed) and graded `good` — a re-sync with no source changes should carry every grade forward at zero cost (confirmed: the conventions-header rebuild in this same session already exercised that carry-forward path).
